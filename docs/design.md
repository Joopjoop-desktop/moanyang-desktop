# 줍줍(Joopjoop) 설계 문서 — MVP

> 흩어진 메시지에서 할 일을 드래그·붙여넣기로 "줍줍"해 블록으로 정리하고 일정으로 만드는 Windows 데스크톱 앱

---

## 1. 개요

### 1.1 서비스 요약

- 사용자가 카톡, 메일 등 어떤 앱에서든 텍스트를 **드래그 또는 복사 후 붙여넣기**로 앱에 넣는다(먹이 주기).
- AI가 텍스트에서 할 일, 시작일, 마감일, 요청자를 뽑아 **블록**으로 만든다.
- 사용자는 블록 안의 **요소**를 끌어서 옮기며 흩어진 정보를 하나의 일로 합치거나 나눈다.
- 블록은 일정(캘린더)으로 배치된다.

### 1.2 타깃

여러 거래처·여러 창구로 날짜가 걸린 요청을 주고받는 B2B 실무자 (1차: 수주형 제조업 내근 영업관리)

### 1.3 MVP 목적

영상 촬영 및 랜딩페이지 검증용. 단, 반응이 좋으면 그대로 실제 제품으로 확장할 수 있도록 **확장성과 유지보수를 고려한 구조**로 설계한다.

### 1.4 핵심 원칙

- **기본은 AI가 채우고, 사람은 빠진 것을 채우거나 고친다.** (먹이 → AI 추출) 블록은 먹이로만 생기고, 사람은 그 안의 요소를 추가·편집하고 라벨·상태를 바꾼다(7.7).
- **할 일과 날짜가 있으면 사람 손 없이 캘린더에 들어간다.** 사람에게는 빠진 것만 묻는다(7.6). 모든 결과를 검토하게 하지 않는다.
- **자동 규칙을 최소화한다.** 상태·라벨은 사용자가 바꿀 때만 바뀐다. 요소·블록 간 우선순위는 두지 않는다.
- **메시지 원문은 저장하지 않는다.** 블록(요소)만 남긴다.

## 2. 전체 아키텍처

### 2.1 구조: 서버 최소형

- 데스크톱 앱이 대부분을 처리하고, 데이터는 **사용자 PC(로컬 DB)에만 저장**한다.
- 서버는 AI 추출 중계, 인증, 사용량 관리 등 최소 역할만 한다.
- 기기 간 동기화는 추후 **사용자가 켰을 때만 동작하는 선택형 동기화**로 추가한다.
- **MVP에서는 서버를 개발하지 않는다.** AI 추출은 목업 또는 개발용 API 직접 호출로 대체한다.

### 2.2 층별 책임

| 층                            | 담당                                                                                                                                         |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **UI 층** (Electron renderer) | 오늘 창(오늘 할 일 + 서랍), 먹이 입력(드래그 드롭·붙여넣기), 스튜디오(캘린더·채워 주세요 목록), 요소 드래그, 일정 화면, 알림 표시, 설정 화면 |
| **코어 층** (Electron main)   | OS 연동, 로컬 DB, 블록·요소 도메인 로직, 추출 요청·큐, 스케줄링, 캘린더 연동, 알림 스케줄러, 서버 통신, IPC 핸들러                           |
| **서버** (MVP 이후)           | AI 중계(API 키 보호, 프롬프트 관리, 응답 검증, 원문 미저장), 인증, 사용량 제한, 업데이트 배포, 결제·라이선스, 선택형 동기화                  |

### 2.3 통신 흐름

```
UI ──(IPC 요청)──▶ 코어 ──(HTTPS)──▶ 서버 ──▶ LLM
UI ◀─(IPC 이벤트)── 코어 ◀──────────── 서버
```

- UI는 서버를 직접 호출하지 않는다. 모든 서버 통신은 코어에서만 한다.
- 서버 → 앱 푸시가 필요해지면 그때 WebSocket/SSE를 추가한다.

## 3. 기술 스택

| 영역             | 선택                                                       |
| ---------------- | ---------------------------------------------------------- |
| 앱 프레임워크    | Electron                                                   |
| 언어             | TypeScript                                                 |
| UI               | React                                                      |
| 프로젝트 뼈대    | **electron-vite** (확정)                                   |
| 로컬 DB          | SQLite (**better-sqlite3**)                                |
| ORM              | **Drizzle ORM** + drizzle-kit (TypeORM에서 변경)           |
| 테스트           | Vitest(단위), Playwright(E2E)                              |
| 코드 품질        | ESLint, Prettier, husky + lint-staged                      |
| 빌드·배포        | electron-builder, electron-updater, GitHub Actions         |
| 에러 수집 (이후) | Sentry (Electron SDK)                                      |
| 제품 분석 (이후) | PostHog / Amplitude / Mixpanel 중 선택 (GA는 랜딩페이지용) |
| 서버 관측 (이후) | Datadog                                                    |
| 대상 OS          | Windows 우선                                               |

**확정 구성: electron-vite + better-sqlite3 + Drizzle ORM + electron-builder**

TypeORM → Drizzle 변경 이유: vite(esbuild)는 TypeORM이 의존하는 데코레이터 메타데이터(`emitDecoratorMetadata`)를 생성하지 못하고, 엔티티·마이그레이션 경로 glob도 번들링과 맞지 않음.

### 3.1 빌드 구성

- electron-vite에서 코어(main) 층은 외부 의존성을 번들에 포함하지 않고 `node_modules`에서 불러오도록 설정한다.
- better-sqlite3는 electron-builder의 설치 후 리빌드(`install-app-deps`)를 `postinstall`에 걸어 Electron 버전에 맞게 자동 리빌드한다.
- 마이그레이션은 drizzle-kit으로 SQL 파일을 생성하고 앱 패키지에 포함되도록 패키징 설정을 한다. 앱 시작 시 미적용 마이그레이션을 순서대로 실행한다.
- 마이그레이션 SQL은 asar 패키지 밖(electron-builder `extraResources`)에 둔다. asar 안에서 읽을 때보다 경로 문제가 적다.
- 마이그레이션 폴더 경로는 개발 모드와 패키징된 앱에서 다르므로 시작 시 환경에 따라 결정한다.

## 4. 저장소 구조

하나의 저장소에서 폴더로 층을 나눈다.

```
joopjoop-desktop/
├─ src/
│  ├─ main/       # 코어 층
│  │  ├─ ipc/          # IPC 핸들러 (Controller 역할)
│  │  ├─ services/     # 도메인 서비스
│  │  ├─ domain/       # 순수 도메인 로직 (Electron 비의존)
│  │  ├─ repositories/ # 저장소 인터페이스·구현 (소프트 딜리트 필터 담당)
│  │  ├─ db/           # Drizzle 스키마, DB 연결, 마이그레이션 실행
│  │  ├─ adapters/     # Extractor, CalendarProvider 등 외부 연동
│  │  ├─ os/           # 창·트레이·클립보드·단축키
│  │  └─ infra/        # Logger, ErrorReporter, Analytics, 설정
│  ├─ preload/    # UI에 허용된 기능만 노출
│  ├─ renderer/   # UI 층
│  └─ shared/     # IPC 요청·응답 타입, 에러 코드, 공통 타입
├─ drizzle/       # drizzle-kit이 생성한 마이그레이션 SQL (패키지에 포함)
└─ package.json
```

서버는 추후 별도 저장소 또는 모노레포(`apps/desktop`, `apps/server`, `packages/shared`)로 추가한다.

## 5. 코어 층 설계

### 5.1 내부 계층

| 계층       | Spring 비유     | 역할                                             |
| ---------- | --------------- | ------------------------------------------------ |
| IPC        | Controller      | UI 요청 수신, 입력 검증, 공통 응답 형식으로 반환 |
| Service    | Service         | 비즈니스 로직, 트랜잭션, 이력 기록               |
| Domain     | Domain          | 요소 이동·충돌 판단 등 순수 로직                 |
| Repository | Repository      | 엔티티 저장·조회, 소프트 딜리트 필터             |
| Adapter    | 외부 API Client | AI 추출, 캘린더 등                               |
| OS         | —               | 창, 트레이, 클립보드, 단축키                     |

### 5.2 설계 원칙

- **인터페이스 + 의존성 주입**: 목업 ↔ 실제 구현을 서비스 코드 변경 없이 교체한다.
  - `Extractor`: `MockExtractor` → `DirectLlmExtractor`(개발용) → `ServerExtractor`
  - `CalendarProvider`: `MockCalendarProvider` → Google / Outlook
  - `Logger`, `ErrorReporter`, `Analytics`
  - `ChangeNotifier`: 서비스가 데이터 변경을 알리는 통로. Electron 구현체가 모든 창에 `blocks:changed`를 보내고, 테스트는 가짜 구현으로 검증한다. (9.4)
  - 저장소(Repository)는 인터페이스 없이 구현 클래스만 둔다. 서비스 테스트를 실제 메모리 DB로 하므로 가짜 저장소가 필요 없다.
- **도메인 로직은 Electron에 의존하지 않는다.** 단독 테스트 가능, 추후 서버로 이전 가능.
- **모든 변경은 서비스 계층을 거친다.** 변경과 이력 기록을 같은 트랜잭션에서 처리한다.
- **트랜잭션은 동기다.** better-sqlite3 + Drizzle 트랜잭션 안에서는 `await`를 쓸 수 없으므로, 트랜잭션 안에는 DB 작업만 둔다. AI 추출 등 비동기 작업은 트랜잭션 밖에서 끝내고 결과 저장만 트랜잭션으로 한다.

### 5.3 모듈별 MVP 범위

| 모듈      | MVP                                        | 이후                                                      |
| --------- | ------------------------------------------ | --------------------------------------------------------- |
| OS 연동   | 오늘 창(투명·항상 위), 스튜디오 창, 트레이 | 전역 단축키, 화면 공유 감지, 자동 실행, 직전 활성 앱 감지 |
| 먹이 수집 | 드래그 드롭, 서랍 클릭 후 붙여넣기         | OCR 영역 캡처, 공식 툴 연동                               |
| 추출      | 목업 또는 API 직접 호출                    | 서버 중계                                                 |
| 블록·요소 | 생성, 편집, 이동, 합치기, 삭제·복구        | —                                                         |
| 저장소    | SQLite + 마이그레이션                      | 로컬 암호화, 선택형 동기화                                |
| 스케줄링  | 날짜 표시 (달력, 7.5)                      | 소요 시간 추정, 빈 시간 배치, 재조정                      |
| 캘린더    | 목업 캘린더                                | Google / Outlook 연동                                     |
| 알림      | —                                          | 마감 임박, 회신 대기, 아침 브리핑                         |

## 6. 데이터 모델

### 6.1 개념

- **블록**은 **요소를 담는 그릇**이다.
- **요소**는 블록 안의 정보 한 조각이다. (할 일, 시작일, 마감일, 요청자, 메모 등)
- 모든 요소는 비어 있을 수 있다. 날짜 없는 할 일, 할 일 없는 날짜 블록 모두 가능.
- **합치기** = 한 블록의 요소들을 다른 블록으로 옮기기
- **분리** = 요소를 끌어내 다른 블록으로 옮기거나 빈 곳에 놓아 새 블록 만들기

### 6.2 엔티티

#### Capture — 먹이를 준 행위

| 필드       | 설명                                                                        |
| ---------- | --------------------------------------------------------------------------- |
| id         | UUID v7                                                                     |
| method     | `drag` / `paste` (이후 `ocr`, `integration` 등 추가)                        |
| sourceApp  | 직전 활성 앱 이름 (예: `KakaoTalk.exe`), null 허용. 창 제목은 저장하지 않음 |
| status     | `pending` / `extracting` / `done` / `failed`                                |
| errorCode  | 실패 시 코드, null 허용 (예: `CAPTURE_EXTRACT_FAILED`, `INTERRUPTED`)       |
| capturedAt | 먹인 시각                                                                   |

- **원문 텍스트는 저장하지 않는다.**
- `sourceApp`은 **코어가 직접** 알아낸다. UI 요청으로 받지 않는다. 직전 활성 앱 감지는 네이티브 모듈이 필요해 MVP 이후로 미루고(5.3), 그전까지는 null.

#### Block — 요소를 담는 그릇

| 필드                  | 설명                                       |
| --------------------- | ------------------------------------------ |
| id                    | UUID v7                                    |
| reviewedAt            | "이대로 두기" 시각, null이면 안 함 (7.6)   |
| completedAt           | 완료 시각, null이면 미완료                 |
| deletedAt             | 소프트 딜리트 시각                         |
| deleteReason          | `user` / `emptied`, 삭제되지 않았으면 null |
| createdAt / updatedAt |                                            |

#### Element — 블록 안의 정보 한 조각

| 필드                  | 설명                                                                              |
| --------------------- | --------------------------------------------------------------------------------- |
| id                    | UUID v7                                                                           |
| blockId               | 속한 블록 (이동 시 변경)                                                          |
| type                  | `task` / `detail` / `start_date` / `due_date` / `requester` / `memo` (확장 가능)  |
| value                 | 텍스트 요소(할 일·상세·요청자·메모)의 값                                          |
| dateValue             | 날짜 요소의 날짜 `YYYY-MM-DD` (인덱스)                                            |
| timeValue             | 시간 언급 시에만 `HH:mm`                                                          |
| rawText               | 날짜 원래 표현 ("다음주 금요일까지"), 상세 표시용                                 |
| needsConfirm          | AI 해석이 애매했는지. 화면에 "확인 필요" 표시, 사용자가 수정하거나 확인하면 꺼짐  |
| captureId             | 출처 먹이, 사용자가 직접 만든 요소(메모 등)는 null                                |
| orderIndex            | 블록 안에서의 순서                                                                |
| deletedAt             | 소프트 딜리트 시각                                                                |
| deleteReason          | `user`(사용자가 직접 삭제) / `discarded`(충돌에서 버려짐), 삭제되지 않았으면 null |
| createdAt / updatedAt |                                                                                   |

- 날짜를 JSON이 아닌 전용 컬럼으로 두는 이유: 캘린더에서 날짜로 조회·정렬하므로 인덱스가 필요하다.
- AI가 처음 뽑은 값은 History에 남으므로 별도 컬럼을 두지 않는다.
- 사용자가 날짜 요소를 수정하면 `rawText`를 비우고 `needsConfirm`을 끈다. 원래 표현은 History에 남는다.

#### Label — 상태 라벨

| 필드     | 설명                                                                 |
| -------- | -------------------------------------------------------------------- |
| id       | UUID v7                                                              |
| key      | 시스템 라벨 식별자 (예: `waiting_reply`), unique. 사용자 라벨은 null |
| name     | 예: 조율 중, 회신 대기                                               |
| isSystem | 시스템 제공 여부 (시스템 라벨은 기능과 연결)                         |
| groupKey | 같은 그룹 안에서는 하나만 붙음                                       |

- 코드는 시스템 라벨을 이름이 아닌 `key`로 찾는다. 이름을 바꿔도 기능이 깨지지 않는다.
- 시스템 라벨 목록은 코드에 두고, **앱 시작 시 `key` 기준으로 없는 라벨만 추가**한다. 이름이 바뀌었으면 갱신한다.

#### BlockLabel — 블록–라벨 N:M

| 필드       | 설명                                 |
| ---------- | ------------------------------------ |
| blockId    |                                      |
| labelId    |                                      |
| attachedAt | 붙인 시각 ("회신 대기 N일째" 계산용) |

#### History — 변경 이력 (추가 전용)

| 필드                  | 설명                                                                                                                                                                      |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| id                    | UUID v7                                                                                                                                                                   |
| entityType / entityId | 대상                                                                                                                                                                      |
| action                | 예: `element.created`, `element.updated`, `element.moved`, `element.deleted`, `element.discarded`, `block.deleted`, `block.reviewed`, `block.completed`, `label.attached` |
| before / after        | 변경 전후 값 (JSON)                                                                                                                                                       |
| occurredAt            |                                                                                                                                                                           |

- 수정·삭제하지 않는다. MVP에서는 기록만 하고 실행 취소·이력 화면은 만들지 않는다.

**기록 범위**

- 서비스가 반영하는 변경은 **전부** 기록한다. 도메인 계산 결과(`MovePlan`)에 담긴 자동 정리, 확인 상태 변경, 빈 블록 삭제, 라벨 해제도 포함한다.

  | 변경                                         | action                                             |
  | -------------------------------------------- | -------------------------------------------------- |
  | 요소 이동(다른 블록, 같은 블록 안 순서 변경) | `element.moved`                                    |
  | 요소 버림(자동 정리·충돌 선택)               | `element.discarded`                                |
  | 확인 상태 변경 등 값 수정                    | `element.updated`                                  |
  | 빈 블록 삭제                                 | `block.deleted` + 떼어진 라벨마다 `label.detached` |
  | 분리로 새 블록 생성                          | `block.created`                                    |
  | 추출로 블록·요소 생성 (8.6)                  | `block.created` + 요소마다 `element.created`       |

- **예외: 다른 요소들의 `orderIndex` 재번호는 기록하지 않는다.** 사용자가 옮긴 요소만 기록한다.

**before / after**

- 바뀐 필드만 기록한다.
- 생성은 `after`에 전체 값, 삭제·버림은 `before`에 전체 값을 기록한다.
- 라벨 붙이기·떼기는 `entityType = 'block'`, `entityId = 블록 ID`로 기록하고 `after`/`before`에 `labelId`를 넣는다.

### 6.3 관계

```
Capture 1 ── N Element
Block   1 ── N Element
Block   N ── M Label   (BlockLabel)
```

### 6.4 공통 규칙

- **ID**: UUID v7 (선택형 동기화 대비, 시간순 정렬 가능). `uuid` 패키지의 `v7()`로 생성
- **삭제**: 소프트 딜리트 → 일정 기간(예: 30일) 경과 후 앱 시작 시 하드 딜리트 (아래 "하드 딜리트")
- **마이그레이션**: MVP부터 적용. drizzle-kit으로 SQL 생성, 앱 시작 시 실행 (3.1 참고)
- **DB 위치**: 배포는 Electron `userData` 경로, 개발은 프로젝트 내 `data/` (`.gitignore` 처리). 파일 이름은 `joopjoop.db`

#### 저장 형식

| 값                                               | 형식                                           | 예시                       |
| ------------------------------------------------ | ---------------------------------------------- | -------------------------- |
| 시각 (`createdAt`, `deletedAt`, `capturedAt` 등) | ISO 8601 문자열, **항상 UTC(`Z`)·밀리초 포함** | `2026-10-04T09:00:00.000Z` |
| 날짜 요소 `dateValue`                            | `YYYY-MM-DD` 문자열 (시간대 없는 달력 날짜)    | `2026-10-09`               |
| 날짜 요소 `timeValue`                            | `HH:mm` 문자열                                 | `11:00`                    |
| 참/거짓 (`isSystem`, `needsConfirm`)             | SQLite 정수 0/1 (Drizzle boolean 모드)         |                            |
| History `before` / `after`                       | JSON 문자열                                    |                            |

- **시각 문자열은 `new Date().toISOString()`으로만 만든다.** 문자열 순서 정렬이 시간 순서와 같으려면 모든 값이 같은 형식이어야 한다. 시각 생성 함수를 한 곳에 두고 그 함수만 사용한다.
- `dateValue`·`timeValue`는 사용자가 본 달력상의 날짜·시간이므로 UTC로 바꾸지 않는다.

#### 외래 키와 인덱스

| 관계                                                   | 삭제 시 동작                                                             |
| ------------------------------------------------------ | ------------------------------------------------------------------------ |
| Element.blockId → Block                                | `ON DELETE CASCADE` (블록을 지우면 요소도 삭제)                          |
| BlockLabel.blockId → Block, BlockLabel.labelId → Label | `ON DELETE CASCADE`                                                      |
| Element.captureId → Capture                            | `ON DELETE SET NULL` (출처 정보만 비우고 요소는 유지)                    |
| History                                                | 외래 키 없음 (여러 종류의 대상을 가리킴). 하드 딜리트 코드에서 직접 삭제 |

- 종류 값(`type`, `status`, `method`, `deleteReason`)은 문자열 컬럼, 허용 값은 TypeScript 타입으로만 제한한다. DB CHECK 제약을 걸지 않는다(종류 추가 시 테이블 재생성 방지).
- `orderIndex`는 정수. 순서가 바뀌면 그 블록의 요소 번호를 다시 매긴다.
- BlockLabel 기본 키는 `(blockId, labelId)`.
- 인덱스: Element `blockId`, Element `dateValue`, Element `captureId`(Capture 하드 딜리트용), History `(entityType, entityId)`.
- DB 컬럼 이름은 snake_case (`block_id`), 코드에서는 camelCase (`blockId`).

#### 블록 updatedAt

- 블록 자체(검토·완료·삭제·라벨)나 **그 안의 요소**(추가·수정·삭제·이동)가 바뀌면 블록의 `updatedAt`을 갱신한다. 이동은 원본·대상 블록 모두 갱신한다.
- 충돌 미리보기 이후 변경 감지에 쓴다. (7.1)

#### 하드 딜리트

앱 시작 시 보관 기간(예: 30일)이 지난 데이터를 지운다.

| 대상    | 조건                                                                 | 함께 지워지는 것                                                   |
| ------- | -------------------------------------------------------------------- | ------------------------------------------------------------------ |
| Block   | `deletedAt`이 기간 경과                                              | 요소·라벨 연결(CASCADE), 블록과 그 요소들의 History(코드에서 직접) |
| Element | 블록이 살아 있어도 요소 자신의 `deletedAt`이 기간 경과               | 그 요소의 History                                                  |
| Capture | 연결된 요소가 없고 `capturedAt`이 기간 경과 (`notTask`, `failed` 등) | —                                                                  |

- 실패 카드를 닫으면(`capture:dismiss`) 그 `failed` Capture는 기간과 상관없이 바로 지운다. 실패한 Capture에는 연결된 요소가 없다(8.6).

#### SQLite 연결 설정

- **외래 키 검사**: SQLite는 기본으로 꺼져 있고 연결마다 초기화되므로, **DB를 열 때마다** `PRAGMA foreign_keys = ON`을 실행한다.
- **WAL 모드**: `PRAGMA journal_mode = WAL`. 쓰는 중에도 읽기가 막히지 않는다.
- 이 설정은 DB 연결 코드 한 곳에서만 처리한다.

### 6.5 소프트 딜리트 판단

- 요소가 살아 있다 = **요소의 `deletedAt`이 null** 이고 **속한 블록의 `deletedAt`도 null**.
- 이 조건은 **저장소 계층 한 곳**에서 처리한다. 요소를 조회하는 모든 기본 메서드가 자동으로 붙인다.
- 삭제된 데이터까지 봐야 하는 경우(복구, 휴지통 목록, 하드 딜리트)만 별도 메서드로 분리한다.
- ORM 기능에 의존하지 않고 저장소 계층에서 직접 처리한다.

## 7. 도메인 규칙

### 7.1 요소 이동 (합치기·분리)

- 요소를 다른 블록에 놓으면 그 블록으로 이동한다.
- 블록을 다른 블록에 놓으면 모든 요소가 이동한다(합치기).
- 요소를 빈 곳에 놓으면 그 요소만 담은 새 블록이 생긴다(분리).
- 블록이 합쳐진 뒤 또 다른 블록이 합쳐져도 계층 없이 하나의 블록에 요소가 추가될 뿐이다.
- 같은 블록 안에서 옮기면 순서 변경이며 충돌 판단을 하지 않는다.
- 분리로 생긴 새 블록은 기본 상태(검토 전, 미완료, 라벨 없음)로 시작한다.

#### 놓는 위치와 순서

- 요소 하나를 끌어다 놓으면 **놓은 위치**에 끼운다. 위치가 없으면 맨 뒤에 놓는다.
- 블록 합치기는 대상 블록 **맨 뒤에 원래 순서대로** 붙인다.
- 순서가 바뀐 블록은 `orderIndex`를 0부터 다시 매긴다. (원본 블록, 대상 블록 모두)

#### 계산과 반영

- 도메인은 "무엇이 바뀌어야 하는지"만 계산하고, 서비스가 그 결과를 DB에 반영하고 History를 기록한다.
- **충돌 확인(`element:checkConflict`)은 미리보기다.** 아무것도 저장하지 않는다.
- **실제 이동(`element:move`, `block:merge`)은 사용자 선택을 받아 자동 정리부터 충돌 처리까지 전체를 다시 계산하고, 한 트랜잭션에 한 번에 반영한다.** 선택이 끝나기 전에 일부(예: 자동 정리)만 저장하지 않는다. 취소하면 데이터가 그대로여야 한다.
- 같은 블록 안 순서 변경은 계산 결과에 옮긴 요소를 명시(`reorders`)해, 서비스가 `element.moved`를 기록할 수 있게 한다.

#### 미리보기 이후 변경 감지

- 선택한 ID가 묶음에 있는지만 보면, 같은 ID의 값이 바뀐 경우(예: 마감일 10/10 → 10/12)를 놓친다.
- 충돌 미리보기 응답에 **원본·대상 블록의 `updatedAt`** 을 함께 돌려준다.
- 충돌 선택이 있는 이동 요청은 이 값을 다시 보낸다. 서비스는 현재 값과 다르면 `CONFLICT_PREVIEW_STALE`로 거부하고, UI는 미리보기를 다시 띄운다.
- 블록 안 요소의 추가·수정·삭제·이동이 모두 블록 `updatedAt`을 갱신하므로(6.4) 이 값 하나로 감지된다.
- 충돌 선택이 없는 이동은 이 값을 받지 않는다. 그사이 충돌이 생겼으면 `CONFLICT_SELECTION_MISSING`으로 걸러진다.

### 7.2 같은 종류 요소 충돌

#### 충돌 대상 여부

요소 종류마다 **"충돌 대상 여부" 속성**을 둔다. 새 종류를 추가할 때는 이 속성만 정한다.

| 묶음                                | 종류                                          | 이동으로 겹치면 |
| ----------------------------------- | --------------------------------------------- | --------------- |
| 충돌 대상 (하나여야 자연스러운 것)  | `task`, `start_date`, `due_date`, `requester` | 충돌 선택       |
| 충돌 아님 (여러 개가 자연스러운 것) | `detail`, `memo`                              | 그냥 뒤에 추가  |

- 날짜 역할: 시작일 + 마감일은 기간이 되며 충돌이 아니다. 마감일 + 마감일, 시작일 + 시작일은 충돌이다.

#### 계산 순서

1. 옮겨오는 요소를 종류별로 나눈다. 충돌 대상이 아닌 종류는 그냥 추가한다.
2. **자동 정리**: 옮겨오는 요소 중 대상 블록에 있던 같은 종류 요소와 값이 같은 것을 버린다.
3. **충돌 선택**: 남은 옮겨오는 요소가 있는 종류마다, 대상 블록의 같은 종류 요소 **전부**와 남은 옮겨오는 요소를 한 묶음으로 만든다. (예: 대상에 마감일 [10/9, 10/10]이 함께 남아 있고 10/11이 들어오면 세 개 중에서 고른다)
4. 옮겨오는 요소가 모두 자동 정리되면 충돌 선택 없이 끝난다.

예: 대상 마감일 [10/9], 옮겨오는 마감일 [10/9, 10/10] → 옮겨온 10/9는 자동 정리, 대상 10/9와 옮겨온 10/10이 충돌 묶음

#### 값이 완전히 같을 때 — 자동 정리

- **자동 정리는 이번 이동으로 겹친 요소에만 적용한다.** 비교는 항상 "옮겨오는 요소 ↔ 대상 블록에 있던 요소" 사이에서만 한다. 대상 블록에 이미 함께 남겨둔 요소끼리는 비교하지 않는다.
- 겹친 요소의 값이 완전히 같으면 **선택 화면 없이 하나로 자동 정리**한다. 이동해 들어온 요소를 버리고 대상 블록에 있던 요소를 남긴다.
- 정리된 요소는 History에 `element.discarded`로 남긴다.
- 같은 값의 기준은 **엄격하게** 둔다.
  - 텍스트: 앞뒤 공백만 정리한 뒤 완전히 일치할 때만
  - 날짜: `dateValue`와 `timeValue`가 같을 때 (`rawText`는 달라도 같은 값으로 본다)
  - "김과장"과 "김 과장"처럼 비슷하기만 한 값은 같은 값으로 보지 않고 선택 화면으로 보낸다.
- 날짜 요소를 자동 정리할 때 둘 중 하나라도 `needsConfirm = false`(확인됨)이면 남는 요소의 `needsConfirm`을 끈다. 이 변경도 History에 `element.updated`로 남긴다.

#### 값이 다를 때 — 충돌 선택

- **사용자가 남길 요소를 고른다.** 여러 개를 함께 남길 수도 있다.
- **묶음마다 최소 하나는 남겨야 한다.** 전부 버리는 것은 "고르기"가 아니라 "삭제"이므로, 지우려면 따로 삭제한다.
- 선택 결과는 **묶음(요소 종류)별 "남길 요소 ID 목록"** 으로 받는다.
- 실제 이동 시 받은 선택을 **현재 충돌 묶음과 다시 대조**한다. 미리보기 이후 데이터가 바뀌었을 수 있다. 다음 경우는 에러 코드로 거부한다.
  - 선택이 빠진 묶음이 있음
  - 묶음에 없는 요소 ID가 들어 있음
  - 묶음에서 하나도 남기지 않음
- **고르지 않은 요소는 버린다.** 요소에 `deletedAt`, `deleteReason = 'discarded'`를 찍고 History에 `element.discarded`로 남긴다. 휴지통에는 보이지 않는다.
- 같은 종류 요소가 여러 개 남으면 **우선순위 없이 모두 동일하게 표시**한다. 마감일이 둘이면 캘린더에도 둘 다 표시한다.

### 7.3 블록 삭제와 빈 블록

- **블록 삭제 시 요소에는 `deletedAt`을 찍지 않는다.** 블록만 삭제 표시하고, 복구하면 연결된 요소가 그대로 돌아온다. (요소에 찍으면 블록 삭제 전에 따로 지운 요소와 구분되지 않아 복구 시 함께 살아난다.)
- 요소 이동으로 블록이 비면 → **자동 소프트 딜리트, `deleteReason = 'emptied'`**. 휴지통에 보이지 않는다. 되돌리기는 이후 이력 기반 실행 취소가 맡는다.
  - **라벨 연결도 제거한다.** 소프트 딜리트는 블록 행을 지우지 않아 CASCADE가 동작하지 않으므로, 이동 결과에 라벨 연결 제거를 포함하고 History에 `label.detached`로 남긴다.
- 사용자가 블록을 삭제하면(`deleteReason = 'user'`, 마지막 요소 삭제 포함) **라벨 연결을 유지한다.** 휴지통에서 복구하면 요소와 함께 라벨도 원래대로 돌아온다.
- 사용자가 요소를 삭제하면 → 요소에 `deletedAt`, `deleteReason = 'user'`를 찍고 History에 `element.deleted`를 남긴다.
- 단, 사용자가 블록의 **마지막 요소를 삭제**하면 → 요소에 `deletedAt`을 찍지 않고 **블록을 `deleteReason = 'user'`로 삭제**한다. 휴지통에 보이고, 복구하면 그 요소도 함께 돌아온다.
  - History는 `block.deleted` **하나만** 남긴다. 요소는 실제로 삭제 상태가 아니므로 `element.deleted`를 남기지 않는다.
  - `after`: `{ deleteReason: 'user', trigger: 'element.delete', elementId }`
- 휴지통 목록은 `deleteReason = 'user'`만 보여준다.
- **9단계부터 휴지통 화면은 없다.** 사용자가 지운 블록은 화면에서 바로 사라지고, 몇 초 동안 뜨는 "되돌리기" 알림(`block:restore`)으로만 살린다. DB 쪽 소프트 딜리트와 30일 뒤 하드 딜리트(6.4)는 그대로 둔다. 휴지통 목록 조회(`block:list`의 `trash`)는 코어에 남겨 두고 화면에서 쓰지 않는다.

### 7.4 상태와 라벨

- 상태 = 이대로 두기 여부(`reviewedAt`), 완료 여부(`completedAt`), 라벨
  - `reviewedAt`은 8단계까지 "검토 완료"였다. 9단계부터는 "날짜 없이 이대로 두기"로 뜻을 좁히고 컬럼은 그대로 쓴다. 블록 분류에서 "날짜 없음" 판단에만 쓰인다(7.6).
- **상태는 사용자가 직접 바꿀 때만 바뀐다.** 요소 이동으로 자동 변경되지 않는다.
- 이대로 두기 한 블록에 새 요소가 합쳐져도 상태는 유지된다. 합치기 자체가 사용자가 요소를 보고 직접 끌어다 놓는 행동이기 때문이다. 합친 결과에 날짜가 생기면 분류 규칙에 따라 캘린더로 간다.
- 새로 생긴 블록은 기본값(이대로 두기 안 함, 미완료, 라벨 없음)으로 시작한다.
- 라벨은 사용자가 직접 붙이고 뗀다. AI는 라벨을 자동으로 붙이지 않는다.
- 시스템 라벨은 기능과 연결된다. (이후: 회신 대기 → N일 후 알림, 조율 중 → 가일정 표시)
- 시스템 라벨 목록:

  | key             | 이름      | groupKey   |
  | --------------- | --------- | ---------- |
  | `coordinating`  | 조율 중   | `progress` |
  | `waiting_reply` | 회신 대기 | `progress` |
  - 둘은 같은 그룹이므로 한 블록에 하나만 붙는다.

- **같은 그룹 라벨을 붙이면 기존 라벨을 뗀다.** 사용자가 직접 라벨을 붙이는 행동이므로 "상태는 사용자가 바꿀 때만 바뀐다" 원칙에 맞다. History에 `label.detached`(기존)와 `label.attached`(새 라벨)를 남긴다. `groupKey`가 없는 라벨은 다른 라벨에 영향을 주지 않는다.
- 이미 붙어 있는 라벨을 다시 붙이면 아무것도 바뀌지 않는다. (`attachedAt` 유지 — "회신 대기 N일째" 계산이 초기화되지 않도록)
- 사용자 정의 라벨은 구조만 지원하고 화면 기능은 MVP 이후에 연다.

### 7.5 캘린더 표시

| 블록의 날짜 요소 | 표시                                |
| ---------------- | ----------------------------------- |
| 날짜 없음        | 캘린더에 안 나오고 목록에만 (7.6)   |
| 마감일만         | 마감일에 표시                       |
| 시작일만         | 시작일에 점으로 표시                |
| 시작일 + 마감일  | 기간 막대                           |
| 마감일 여러 개   | 각 날짜에 모두 표시 (우선순위 없음) |

**여러 날짜가 섞였을 때** (합치기로 같은 종류가 여러 개 남을 수 있다, 7.2)

- 시작일만 여러 개면 각 시작일에 점.
- 시작일과 마감일이 다 있으면 **가장 이른 시작일 ~ 가장 늦은 마감일**을 기간 막대로 그린다.
- 막대 위에서도 **개별 시작일(점)과 마감일(마감 표시)은 모두 그대로** 표시한다.
- 가장 이른 시작일이 가장 늦은 마감일보다 늦으면(뒤집힘) 막대 없이 각 시작일 점과 각 마감일 표시만 그린다.
- 날짜 없이 원래 표현만 있는 요소(예: "다음주쯤")는 달력에 나오지 않는다(목록에만, 7.6).

**보여주는 블록**

- 삭제되지 않은 블록 전부(이대로 두기 여부와 상관없음). 완료한 블록은 흐리게, "확인 필요" 날짜는 점선 테두리.
- 항목 글자는 할 일 값. 할 일이 없으면 요청자 → 상세 → "(할 일 없음)". 시간이 있으면 앞에 붙인다.

**계산 위치와 조회**

- 블록 → 달력 표시(막대·점·마감 표시) 계산은 **코어 도메인의 순수 함수**다. 나중에 외부 캘린더로 내보낼 때도 같은 계산을 쓴다.
- `calendar:list({ from, to })`는 조회 기간과 겹치는 블록만 돌려준다.
  - 조회 기간 안에 날짜가 하나도 없어도, **기간 막대가 조회 기간 전체를 가로지르는 블록은 포함**한다(예: 9월 시작 ~ 11월 마감 블록은 10월 달력에 막대로 나온다).
  - 후보는 `dateValue` 인덱스로 "가장 이른 날짜 ≤ `to` 이고 가장 늦은 날짜 ≥ `from`"인 살아 있는 블록을 찾고, 표시를 계산한 뒤 기간과 실제로 겹치는 것만 남긴다.
  - `from`·`to`는 `YYYY-MM-DD`이고 실제 있는 날짜여야 한다. `from`이 `to`보다 늦으면 `INVALID_INPUT`.
- "목업 캘린더"는 우리 블록만 보여주는 앱 안의 월간 달력이다. 외부 캘린더용 `CalendarProvider`는 실제 연동할 때 만든다.

**화면** (9.6 스튜디오 가운데. 9단계부터 스튜디오의 메인)

- 월간 보기만. 일요일 시작, 지난달·다음달·오늘 버튼. 주간 보기는 이후.
- 하루 칸에 3개까지, 나머지는 "+N개". 막대가 주를 넘어가면 주마다 나눠 그린다.
- 항목을 누르면 오른쪽 패널이 블록 카드(`BlockCard`)로 바뀌어 그 자리에서 수정한다(9.6). 달력 위에서 끌어서 날짜 바꾸기, 목록 카드를 달력 칸에 끌어다 날짜 넣기는 하지 않는다(이후).
- 월 → 달력 칸(6주 × 7일) 계산은 화면 쪽 순수 함수. 캐시 이름표는 `['blocks', 'calendar', from, to]`라서 `blocks:changed`로 그대로 다시 불러온다.

### 7.6 블록 분류 (캘린더 / 채워 주세요 / 날짜 없는 일)

필수는 **할 일 + 날짜** 두 가지다. 둘 다 있으면 사람 손 없이 캘린더에 들어가고, 빠진 블록만 사람에게 묻는다. 분류는 **상태가 아니라 조건**이라, 빠진 것을 채우면 저절로 목록에서 빠진다.

**용어**

- **할 일 있음**: 살아 있는 `task` 요소가 하나 이상.
- **날짜 있음**: `dateValue`가 있는 `start_date`·`due_date` 요소가 하나 이상. 시작일만 있어도 된다. 원래 표현만 있는 요소(`dateValue` null)는 날짜로 치지 않는다.
- **날짜 확인 필요**: `dateValue`가 있는 날짜 요소 중 하나라도 `needsConfirm`.

**빠진 것** (`missing`, 한 블록에 여러 개일 수 있다. 아래 순서로 나열)

| 값            | 조건                       | 해결 방법                  |
| ------------- | -------------------------- | -------------------------- |
| `task`        | 할 일 없음                 | 할 일 추가 또는 블록 삭제  |
| `date`        | 날짜 없음                  | 날짜 추가 또는 이대로 두기 |
| `dateConfirm` | 날짜 있음 + 날짜 확인 필요 | "확인" 또는 날짜 수정      |

**어디에 나오나** (삭제·완료한 블록은 목록에 나오지 않는다)

| 묶음         | 조건                                                                         |
| ------------ | ---------------------------------------------------------------------------- |
| 채워 주세요  | `task` 빠짐, 또는 `dateConfirm` 빠짐, 또는 (`date` 빠짐 + 이대로 두기 안 함) |
| 날짜 없는 일 | 할 일 있음 + 날짜 없음 + 이대로 두기 함                                      |
| 캘린더       | 날짜 있음 (7.5). "확인 필요"는 점선으로 그리면서 채워 주세요에도 나온다      |

- `reviewedAt`(이대로 두기)은 `date` 판단에만 쓴다. 이대로 두기 한 블록이라도 할 일이 지워지면 다시 채워 주세요에 나온다. 날짜가 생기면 날짜 없는 일에서 빠져 캘린더로 가고, 날짜를 다시 지우면 날짜 없는 일로 돌아온다.
- 날짜 없이 할 일만 남은 완료 블록은 어디에도 보이지 않는다. 완료 직후 "되돌리기" 알림으로만 되돌린다.
- "이대로 두기" 버튼은 화면에서 할 일이 있고 `date`만 빠졌을 때 보여준다. 코어는 막지 않는다. 다른 블록에 `reviewedAt`이 붙어도 위 규칙상 분류가 바뀌지 않는다(8단계 이전에 "검토 완료"한 블록도 같다).
- 계산은 **코어 도메인의 순수 함수** 하나가 맡는다. 목록 조회(`block:list`)와 `BlockView.missing`, 추출 완료 개수(`capture:completed`)가 모두 이 함수를 쓴다.
- 조회: DB에서 "삭제·완료되지 않은 블록"을 후보로 고르고, 서비스에서 이 함수로 거른다(7.5 캘린더 조회와 같은 방식).
- 두 목록 모두 최근 블록이 위(`createdAt` 내림차순).

### 7.7 요소 직접 추가

- 사람이 메모뿐 아니라 **모든 종류의 요소**를 블록에 추가할 수 있다(1.4).
- 충돌 대상 종류(`task`, `start_date`, `due_date`, `requester`, 7.2)는 **블록에 그 종류가 없을 때만** 추가한다. 이미 있으면 `ELEMENT_KIND_EXISTS`. 있으면 추가 대신 수정한다.
  - 합치기로 같은 종류가 이미 여러 개 남은 블록은 그대로 둔다(추가만 막는다).
- `detail`, `memo`는 언제든 추가한다.
- 값 검사는 수정(`element:update`)과 같다. 글자 종류는 앞뒤 공백을 지운 뒤 빈 값이면 `ELEMENT_VALUE_INVALID`. 날짜 종류는 실제로 있는 날짜 필수, 시간은 선택(`HH:mm`).
- 만든 요소는 `rawText` null, `needsConfirm` false, `captureId` null. History `element.created`(`after`에 전체 값), 블록 `updatedAt` 갱신(6.4).
- **넣는 자리**: 종류 순서 **할 일 → 상세 → 시작일 → 마감일 → 요청자 → 메모**(8.6과 같음)에서, **자기 종류와 그 앞 종류** 요소 중 블록 안에서 가장 뒤에 있는 것 바로 뒤에 넣는다(예: 메모를 또 추가하면 마지막 메모 뒤, 마감일은 시작일·상세·할 일 중 가장 뒤의 것 뒤). 그런 요소가 없으면 맨 앞에 넣는다. 사람이 순서를 바꿔 놓았어도 이 계산으로 정한다. 다른 요소들의 `orderIndex`는 다시 매긴다(History 없음, 6.2 예외).
- 계산(추가 가능 여부, 넣는 자리)은 도메인 순수 함수, 반영은 서비스가 한 트랜잭션에서.

## 8. 추출 (AI)

### 8.1 흐름 (비동기)

1. UI → `capture:submit` (원문 텍스트, 방식)
2. 코어: Capture 생성(`pending`), 즉시 응답 → 서랍 "정리하는 중…"
3. 코어: 추출 큐에서 `Extractor` 호출(`extracting`)
4. 성공 → Block·Element 생성, Capture `done` → `blocks:changed`, 이어서 `capture:completed { captureId, blockIds, toCalendar, needsInput }` 이벤트
   - `toCalendar`: 만든 블록 중 빠진 것이 없는 블록 수(바로 캘린더에 들어감). `needsInput`: 채워 주세요로 간 블록 수(7.6). 만들어진 직후라 둘의 합은 `blockIds` 길이와 같다.
   - `notTask: true`이면 블록 없이 `done`, `blockIds`는 빈 배열 → 서랍 "할 일이 안 보여요"
5. 실패 → Capture `failed` → `capture:failed { captureId, errorCode, canRetry }` 이벤트

```
pending ──(큐에서 꺼냄)──▶ extracting ──성공──▶ done
   ▲                          │
   └──(자동 재시도 대기)───────┤
                              └──실패·재시도 초과──▶ failed ──(capture:retry)──▶ pending
```

- 중간 상태(`pending` → `extracting`) 이벤트는 보내지 않는다. 서랍 표시는 submit 응답과 미완료 먹이 수로 충분하다.
- 추출 입력의 `timezone`은 코어가 `Intl.DateTimeFormat().resolvedOptions().timeZone`로 PC 설정을 읽는다.

### 8.2 원문 처리

- 원문은 **추출 큐의 메모리에만** 보관한다. DB에 저장하지 않는다.
  - 성공하면 즉시 지운다.
  - 실패해도 앱이 켜져 있는 동안은 보관해 "다시 시도"를 할 수 있게 한다. 실패 카드를 닫으면(`capture:dismiss`) 지운다.
- `capture:submit`은 **20,000자**를 넘는 텍스트를 `INVALID_INPUT`으로 거절한다. 실수로 큰 텍스트를 붙여넣는 경우를 막는다.
- 네트워크 오류 시 앱이 켜져 있는 동안 간격을 두고 **자동 재시도**한다. (8.7)
- 처리 중·대기 중인 먹이가 있을 때 앱을 종료하면 **확인을 받는다.**
- 계속 실패하면 스튜디오 먹이 칸 아래에 **실패 카드**를 띄우고, 원문이 메모리에 있는 동안 "다시 시도"를 제공한다. 실패 카드 목록은 `capture:listFailed`로 조회한다(앱을 다시 켰을 때도 그릴 수 있도록).
- **앱 시작 시** `pending`·`extracting` 상태인 Capture는 `failed`, `errorCode = 'INTERRUPTED'`로 바꾼다. 원문이 없으므로 "다시 시도" 없이(`canRetry: false`) "처리하지 못했어요, 다시 먹여주세요" 실패 카드만 보여준다.

### 8.3 입력 형식

```ts
type ExtractInput = {
  text: string // 원문 (메모리에서만 사용)
  capturedAt: string // 날짜 계산 기준
  timezone: string // 예: "Asia/Seoul"
}
```

### 8.4 출력 형식

```ts
type DateValue = {
  date: string | null // "2026-10-09"
  time: string | null // 시간 언급 시에만 "11:00"
  rawText: string | null // 원래 표현 "다음주 금요일까지"
  ambiguous: boolean // 해석이 애매하면 true → Element.needsConfirm
}

type ExtractOutput = {
  schemaVersion: 1
  notTask: boolean // 할 일이 없는 내용이면 true, items는 빈 배열
  items: Array<{
    task: string | null
    detail: string | null
    requester: string | null
    startDate: DateValue | null
    dueDate: DateValue | null
  }>
}
```

- **먹이 하나에서 블록 여러 개**가 나올 수 있다. `items` 하나당 블록 하나.
- 추출은 **애매하면 나누는 방향**으로 한다. 잘게 나눈 실수는 사용자가 합치면 되지만, 묶어버린 실수는 고치기 어렵기 때문이다.
- 날짜는 **시작일과 마감일 역할을 구분**한다. 역할이 애매하면 마감일로 처리한다.
- 같은 먹이에서 나온 블록은 목록(7.6)에서 나란히 표시한다.
- 추출 모델은 저렴한 모델로 충분하다(짧은 텍스트에서 정해진 형식 추출).

### 8.5 출력 검증·정리

`Extractor`가 돌려준 값은 코어가 그대로 믿지 않고 zod로 검사한 뒤 정리한다. MockExtractor와 실제 추출기(11단계)에 똑같이 적용한다.

- **구조가 틀리면**(필드 누락, 타입 오류, `schemaVersion` 불일치) 재시도할 수 없는 실패(`CAPTURE_EXTRACT_FAILED`).
- 글자는 앞뒤 공백을 지우고, 빈 문자열은 null로 바꾼다.
- **날짜는 형식뿐 아니라 실제로 있는 날짜인지 검사한다.** `YYYY-MM-DD`이고 달력에 있는 날이어야 한다(`2026-02-30`, `2026-13-01`은 틀림).
- **시간은 `HH:mm`, 00:00 ~ 23:59**.
- 틀린 날짜는 null로 바꾸고 `ambiguous`를 켠다. `rawText`는 남긴다. 틀린 시간은 버리고 `ambiguous`를 켠다.
  - 날짜 하나 때문에 할 일·요청자까지 잃지 않도록 먹이 전체를 실패로 만들지 않는다.
- 날짜가 없는데 시간만 있으면 시간을 버린다.
- `date`와 `rawText`가 모두 null인 날짜 값은 없는 것(null)으로 본다.
- 내용이 모두 빈 item은 버린다. 남은 item이 없으면 `notTask`와 같게 처리한다.

### 8.6 결과 반영

- item 하나 = 블록 하나. 요소 순서는 **할 일 → 상세 → 시작일 → 마감일 → 요청자**. 값이 null인 요소는 만들지 않는다.
- 날짜 요소: `dateValue`가 null이어도 `rawText`가 있으면 만든다(예: "다음주쯤"). 이때 `needsConfirm`을 켠다. 그 밖에는 `needsConfirm = ambiguous`.
- 요소마다 `captureId`를 넣는다.
- 먹이 하나에서 나온 **블록 전부와 Capture `done` 변경을 한 트랜잭션**에서 처리한다. 블록이 반만 생기는 일이 없다.
- History: 블록마다 `block.created`, 요소마다 `element.created`(`after`에 전체 값). AI가 처음 뽑은 값이 여기에 남는다(6.2).
- 블록은 `reviewedAt` null로 만든다. 어디에 나올지는 요소에 따라 정해진다(7.6): 할 일과 날짜가 있으면 캘린더에만, 빠진 것이 있으면 채워 주세요에도.
- 커밋 후 `blocks:changed`, 이어서 `capture:completed`를 보낸다. 실패 처리에서는 블록이 생기지 않으므로 실패한 Capture에는 연결된 요소가 없다.

### 8.7 추출 큐와 재시도

- **한 번에 하나씩, 들어온 순서대로** 처리한다.
- `Extractor`의 실패는 **재시도 가능**(네트워크 등)과 **재시도 불가**(출력 형식 오류 등)로 나눈다.
- 재시도 가능한 실패는 **최대 3번** 자동 재시도한다. 간격은 **2초, 10초, 30초**.
  - 기다리는 동안 상태는 `pending`으로 돌려 두고, 큐는 다음 먹이를 먼저 처리한다. 한 먹이가 기다리는 동안 뒤의 먹이가 막히지 않는다.
  - 재시도 횟수를 넘거나 재시도 불가 실패면 `failed`(`CAPTURE_EXTRACT_FAILED`).
- **수동 다시 시도**(`capture:retry`)는 `failed` 상태이고 원문이 메모리에 있을 때만 된다. 그 외에는 `CAPTURE_NOT_RETRYABLE`. 재시도 횟수는 처음부터 다시 센다.
- **중복 처리 방지**
  - 같은 Capture는 큐에 한 번만 들어간다.
  - 자동 재시도를 기다리는 동안(`pending`) 들어온 수동 다시 시도는 거절한다.
  - 다시 시도를 연달아 호출하면 두 번째는 거절한다(첫 호출에서 `pending`이 되므로).
  - 이미 처리됐거나 닫힌 먹이에 늦게 도착한 재시도 타이머는 아무것도 하지 않는다.

진짜 AI 대신 규칙으로 동작하는 개발용 추출기. 11단계 전까지 개발·배포 빌드 모두 이것을 쓴다.

## 9. IPC 명세

### 9.1 규칙

- 이름: `도메인:동작`
- 요청·응답 타입은 `src/shared`에 정의하고 UI와 코어가 공유한다. (Swagger 역할)
- UI는 preload가 노출한 함수로만 코어를 호출한다.
- **채널 계약은 `src/shared` 한 곳에 정의한다.** preload 함수와 코어 핸들러 타입이 모두 이 계약에서 나온다. 채널을 추가할 때 계약만 고치면 양쪽 타입이 맞춰진다.
- `window.api`는 **도메인별 함수**로 노출한다. 예: `window.api.block.list('needsInput')`, `window.api.element.move({...})`
- **입력 검증은 IPC 계층에서 zod로 한다.** UI가 보낸 값은 실행 중에 검사하고, 형식이 틀리면 `INVALID_INPUT`으로 돌려준다.
- 핸들러는 "입력 → `IpcResult`" 함수로 만들어 Electron 없이 테스트한다. `ipcMain` 등록은 얇게 분리한다.
- 서비스 조립(composition root)은 한 곳에서 하고, IPC 등록이 이를 받아 쓴다.
- **개발 모드 전용 채널**(`dev:*`)은 코어가 개발 모드에서만 등록하고, preload도 빌드 시점 값(`import.meta.env.DEV`)으로 개발 빌드에만 포함한다. 배포 빌드에는 코드 자체가 없다.

### 9.2 공통 응답 형식

```ts
type IpcResult<T> = { ok: true; data: T } | { ok: false; error: { code: string; message: string } }
```

- 코어는 예외를 그대로 던지지 않고 이 형식으로 감싸 반환한다.
- 에러 코드는 도메인별로 정의한다(`src/shared/errors.ts`). 예: `BLOCK_NOT_FOUND`, `ELEMENT_NOT_FOUND`, `CAPTURE_EXTRACT_FAILED`, `INTERRUPTED`, `CAPTURE_NOT_FOUND`, `CAPTURE_NOT_RETRYABLE`, `CONFLICT_SELECTION_MISSING`, `CONFLICT_SELECTION_INVALID`, `CONFLICT_SELECTION_EMPTY`, `CONFLICT_PREVIEW_STALE`, `ELEMENT_VALUE_INVALID`, `ELEMENT_KIND_EXISTS`, `LABEL_NOT_FOUND`, `INVALID_INPUT`
- 사용자에게 보여줄 문구는 UI가 코드 기준으로 결정한다.
- 정의되지 않은 에러는 `INTERNAL_ERROR`로 반환하고 상세는 로그·에러 수집에만 남긴다.
- 변환 규칙: `DomainError`는 코드를 그대로, 입력 검증 실패는 `INVALID_INPUT`, 그 밖의 예외는 `INTERNAL_ERROR`(메시지에 내부 정보를 넣지 않음).

### 9.4 이벤트 (코어 → UI)

| 채널                        | 설명                                                                                                     |
| --------------------------- | -------------------------------------------------------------------------------------------------------- |
| `capture:completed`         | 추출 완료 `{ captureId, blockIds, toCalendar, needsInput }` (8.1). 빈 배열이면 할 일 없음 (서랍 문구)    |
| `capture:failed`            | 추출 실패 `{ captureId, errorCode, canRetry }`                                                           |
| `capture:unfinishedChanged` | 미완료 먹이 수 변경 `{ count }` (서랍 "정리하는 중…")                                                    |
| `blocks:changed`            | 데이터 변경 `{ blockIds }`, 목록 갱신 필요                                                               |
| `studio:openBlock`          | 스튜디오에 블록 카드 열기 `{ blockId }`. `window:openStudio`에 `blockId`가 있을 때 스튜디오 창에만 (9.7) |

**`blocks:changed` 발생 규칙**

- **서비스가 트랜잭션 커밋 이후 `ChangeNotifier`로 바뀐 블록 ID를 알린다.** IPC 요청이든 추출 큐든 변경 경로와 상관없이 이벤트가 나간다. IPC 계층은 따로 보내지 않는다.
- Electron 구현체가 열린 모든 창에 보낸다.
- 커밋 전에 알리지 않는다. 트랜잭션이 취소되면 알림도 없다.
- **알림이 실패해도 서비스는 성공으로 끝난다.** 이미 커밋된 변경이므로, Electron 구현체가 에러를 로그만 남긴다.
- 아무것도 바뀌지 않은 호출(이미 그 상태 등)은 알리지 않는다.
- 하드 딜리트는 알리지 않는다. 창이 뜨기 전에 실행된다.

**`capture:*` 이벤트**

- 같은 `ChangeNotifier`가 보낸다(창에 보내는 통로를 하나로 유지).
- 추출 성공은 `blocks:changed` 다음에 `capture:completed`가 간다. 화면이 목록을 갱신한 뒤 서랍이 결과를 보여준다.
- 앱 시작 시 `INTERRUPTED` 처리는 이벤트를 보내지 않는다. 창이 뜬 뒤 `capture:listFailed`로 조회한다.
- **미완료 먹이 수는 추출 큐가 기준이다.** 대기 + 처리 중 + 자동 재시도 대기를 센다. 어느 창에서 먹였든(오늘 창·스튜디오), 수동 다시 시도든 자동 재시도 대기 진입·재개든 같은 수에 반영된다.
  - 수가 **실제로 바뀔 때만** `capture:unfinishedChanged`를 보낸다.
  - 창은 처음 뜰 때 `capture:unfinishedCount`로 한 번 조회하고 이후 이벤트로 갱신한다.

### 9.5 화면(renderer)의 코어 연결

- 화면은 `window.api`만 호출한다. `IpcResult`가 실패면 에러 코드를 담은 `ApiError`로 바꿔 던진다.
- 데이터는 **TanStack Query**로 불러오고 캐시한다.
  - 코어 이벤트가 데이터 갱신의 기준이다. 화면은 같은 데이터를 시간이 지났다고 다시 불러오지 않고, 이벤트를 받으면 해당 목록을 다시 불러온다(invalidate).
  - 응답을 받은 뒤 다시 불러와 그린다. **낙관적 업데이트는 하지 않는다**(로컬 DB라 응답이 빠르고, 실패 시 되돌리는 코드가 복잡해진다).
  - 실패한 요청은 자동으로 다시 보내지 않는다. 에러 코드는 대부분 사용자 조작의 결과라 다시 보내도 같다.
- 이벤트 구독

  | 이벤트              | 다시 불러올 것 |
  | ------------------- | -------------- |
  | `blocks:changed`    | 블록 목록      |
  | `capture:completed` | 블록 목록      |
  | `capture:failed`    | 실패 카드 목록 |
  - `capture:retry`, `capture:dismiss`가 성공했을 때도 실패 카드 목록을 다시 불러온다.
  - 구독은 앱 최상단 한 곳에서 하고, 화면이 사라질 때 `window.api.on`이 돌려준 해제 함수로 해제한다. 개발 모드 핫 리로드에서 구독이 쌓이지 않는다.

- **에러 문구**: 에러 코드 → 한국어 문구 표를 화면 쪽 한 곳에 둔다. `INTERNAL_ERROR`와 알 수 없는 오류는 일반 문구만 보여준다.

### 9.6 스튜디오 화면

9단계에서 탭 구조(검토함 / 전체 / 완료 / 휴지통 / 캘린더)를 없애고 **캘린더 중심의 한 화면**으로 바꿨다.

```
┌──────────────────────────────────────────────────────────┐
│ 먹이 칸(붙여넣기) / 실패 카드                            │
├────────────────────────────────────┬─────────────────────┤
│ 캘린더 (7.5)                       │ 오른쪽 패널         │
│                                    │  채워 주세요 N      │
│                                    │  날짜 없는 일 M     │
└────────────────────────────────────┴─────────────────────┘
```

- 페이지 이동 라이브러리(router) 없이 상태값으로 오른쪽 패널 내용을 바꾼다.
- 스타일은 CSS Modules + CSS 변수. UI 라이브러리는 쓰지 않는다.
- **위: 먹이 칸.** 붙여넣기 입력창(`method: 'paste'`), 그 아래 실패 카드. "다시 시도"는 `canRetry`일 때만, "닫기"는 항상.
- **가운데: 캘린더**(7.5). 완료한 블록은 흐리게 남는다.
- **오른쪽: 목록 패널.** 항상 열려 있고 두 묶음을 보여준다(7.6, `block:list`의 `needsInput`, `undated`).
  - 항목은 **한 줄**: 제목(7.5 항목 글자와 같은 규칙) + 빠진 것 하나(`task` → "할 일 없음", `date` → "날짜 없음", `dateConfirm` → "날짜 확인", 여러 개면 이 순서의 첫 번째).
  - 항목을 누르면 **그 자리에서 블록 카드가 펼쳐진다.** 한 번에 하나만 펼치고, 다른 항목을 누르면 이전 것은 접힌다.
  - 펼친 카드의 버튼: "이대로 두기"(할 일 있고 `date`만 빠졌을 때만, 7.6), "삭제". 완료는 카드 맨 위 체크박스로 한다(아래).
  - 빠진 것을 채우면 항목이 목록에서 사라진다(조건이므로 따로 처리하지 않는다).
  - 같은 먹이의 블록은 만들어진 시각이 같아 붙어 나온다(따로 묶지 않음).
- **캘린더 항목을 누르면** 오른쪽 패널이 그 블록 카드로 바뀌고 위에 "← 목록"이 생긴다. 카드에서 삭제·완료하면 목록으로 돌아간다. "+N개"를 누르면 그날의 블록 목록.
- **완료 체크박스** (10단계): 블록 카드 맨 위(날짜 옆)에 체크박스. 체크하면 `block:complete`, 다시 누르면 `block:reopen`. 블록 단위 완료다(할 일 요소마다 체크하지 않음). 카드 아래 "완료/완료 취소" 버튼은 없다. 캘린더 칸과 오른쪽 목록의 한 줄 항목에는 체크박스를 두지 않는다(칸이 작고, 목록은 채우는 게 먼저).
- **스튜디오에서 열기** (10단계): `studio:openBlock`을 받으면 오른쪽 패널을 그 블록 카드로 바꾼다(캘린더 항목을 누른 것과 같음).
- **블록 조작**: 이대로 두기·완료·삭제 뒤 몇 초 동안 "되돌리기" 알림(`reviewed: false` / `reopen` / `restore`). 휴지통 화면이 없으므로 삭제 복구는 이 알림뿐이다(7.3). 이동·합치기는 되돌리기가 없다(이력 기반 실행 취소는 MVP 이후).
- **알림 쌓기**: 알림이 하나뿐이면 삭제 직후 다른 알림이 와서 되돌리기 버튼을 덮는다. 그래서 여러 개를 쌓는다.
  - 최대 3개. 새 알림이 아래에 붙고, 각각 5초 동안 떠 있다.
  - 넘치면 **버튼 없는 알림** 중 가장 오래된 것부터 뺀다.
  - 쌓인 알림이 **전부 되돌리기(버튼 있는) 알림이면 빼지 않고** 잠시 3개를 넘겨 보여준다. 시간이 지나 하나씩 사라지면 다시 3개 이하로 돌아온다.
  - 버튼을 누르면 그 알림만 닫고 동작을 실행한다. 쌓기 규칙은 화면 쪽 순수 함수로 테스트한다.
- **요소 편집**: 클릭해서 그 자리에서 수정한다(글자는 입력칸, 날짜는 날짜칸 + 시간칸). "확인 필요" 옆에 "확인" 버튼, 마우스를 올리면 삭제 ×.
- **요소 추가**: 카드 아래 "+ 추가"(7.7). 누르면 지금 추가할 수 있는 종류만 메뉴로 보여준다(이미 있는 할 일·시작일·마감일·요청자는 빠짐, 상세·메모는 항상). 고르면 "+ 추가" 자리에 빈 편집칸이 열리고, 저장하면 코어가 정해진 자리에 넣는다. 추가할 수 있는 종류는 코어가 `BlockView.addable`로 알려준다. 날짜 종류는 날짜 필수·시간 선택. 빈 채로 나가면 아무것도 만들지 않는다.
- **날짜 표시**: `10/9(금) 11:00`. 원래 표현(`rawText`)은 작은 글씨로 함께 보여준다. 날짜 없이 표현만 있으면 표현 + "확인 필요".
- **추출 완료 알림**: `capture:completed`의 `toCalendar`·`needsInput`으로 "캘린더에 N개 넣었어요" / "N개는 채워 주세요"(둘 다 있으면 이어서). 블록이 없으면 "할 일이 안 보여요".
- **드래그** (`@dnd-kit/core` + `@dnd-kit/sortable`, 7.1). 오른쪽 목록 패널 안에서만 한다.

  | 무엇을             | 어디에          | 동작                                        |
  | ------------------ | --------------- | ------------------------------------------- |
  | 요소               | 같은 카드 안    | 순서 바꾸기 (`reorder`)                     |
  | 요소(펼친 카드)    | 다른 항목       | 미리보기 → 충돌 없으면 이동, 있으면 선택 창 |
  | 요소(펼친 카드)    | 목록 아래 빈 곳 | 새 블록으로 분리 (`new`)                    |
  | 항목(한 줄 손잡이) | 다른 항목       | 합치기: 미리보기 → 이동 또는 선택 창        |
  - 캘린더로 끌어다 놓기, 캘린더에만 있는 블록끼리 합치기는 이후.

- **충돌 선택 창** (7.2)
  - 처음에는 대상 블록에 원래 있던 요소에 체크한다.
  - 묶음마다 하나 이상 골라야 "확인"이 켜진다. 취소하면 아무것도 바뀌지 않는다.
  - `CONFLICT_PREVIEW_STALE`이면 미리보기를 다시 받고 "내용이 바뀌어서 다시 확인해 주세요"를 보여준다. 이전 선택은 **ID와 값(`value`, `dateValue`, `timeValue`)이 모두 그대로인 요소만** 유지하고, 값이 바뀌었거나 새로 생긴 요소는 기본값으로 돌아간다. `rawText`는 비교하지 않는다(7.2 같은 값 기준과 동일).
  - 다시 받은 미리보기에 고를 게 없으면(그사이 겹치던 요소가 사라짐) 창을 닫고 그대로 옮긴다. 충돌이 없을 때 바로 옮기는 것과 같다.
- **테스트**: 화면 쪽 순수 계산(놓은 위치 → api 호출, 충돌 선택 상태, 날짜 표시 형식, 이벤트 → 다시 불러올 목록, 알림 쌓기, 추가 메뉴 종류, 완료 문구)만 Vitest로 테스트한다. 컴포넌트를 그리는 테스트는 12단계 E2E로 미룬다.

### 9.7 오늘 창과 트레이

7단계의 캐릭터 창을 10단계에서 **오늘 창**으로 바꿨다. 캐릭터는 평소 떠 있어도 쓸모가 없어서, 오늘 할 일을 보여줘 켜 둘 이유를 만든다. 먹이 받기는 창 아래 **서랍**이 맡는다.

```
┌──────────────────┐
│ 오늘 10/10(토) ⚙ ▾ │  머리줄: 끌어서 이동, 투명도, 접기
├──────────────────┤
│ ☐ 11:00 회의실 예약 마감│  오늘 할 일 (줄을 누르면 펼침)
│ ☐ 분기 보고서   기간  │
│ ☑ 견적서 송부        │  끝낸 일은 줄 긋고 아래로
├──────────────────┤
│ ▤ 끌어다 놓거나 Ctrl+V │  서랍: 먹이 받기
│   채워 주세요 2  →   │
└──────────────────┘
```

- **창 구조**: 창 만들기·보이기는 코어의 `src/main/os/`가 맡는다. 화면 진입점은 `index.html`(스튜디오)과 `overlay.html`(오늘 창) 두 개이고, `api/` 폴더·공유 타입·preload(`window.api`)는 같이 쓴다.
- **오늘 창**: 폭 260px 고정, 높이 기본 420px. 투명·테두리 없음·항상 위·작업표시줄에 안 보임. 보일 때 다른 앱의 초점을 뺏지 않는다.
  - 처음에는 주 모니터 작업 영역 오른쪽 위. 위치와 높이는 `userData`의 설정 파일(JSON)에 저장하고, 저장된 위치가 현재 화면 밖이면 기본 위치로 돌린다.
  - 머리줄을 끌어 창을 옮긴다(`-webkit-app-region: drag`).
  - **세로 크기 조절**: 투명·테두리 없는 창은 Windows에서 가장자리 끌기 크기 조절이 되지 않을 수 있어 먼저 직접 확인한다. 되지 않으면 창 아래 손잡이를 끄는 동안 화면이 코어에 높이를 보내고 코어가 창 높이를 바꾼다(확인 결과를 여기에 적는다).
  - 투명 부분의 클릭 통과는 하지 않는다. 그래서 접을 때는 화면만 접지 않고 **창 높이를 머리줄 높이로 줄인다**.
- **투명도**: 머리줄 ⚙의 슬라이더로 30~100%(기본 90%). 마우스를 올리면 100%. 화면(CSS)에서 적용하고 값은 `today:setOpacity`로 저장한다.
- **접기·펼치기**
  - 창 전체: 접으면 머리줄만 남고 "오늘 N"(안 끝낸 수)을 보여준다. `today:setCollapsed`로 코어가 창 높이를 바꾸고 상태를 저장한다. 접혀 있어도 머리줄에 글을 놓으면 먹이로 받는다.
  - 할 일 한 줄: 누르면 요청자·상세·메모 등이 그 자리에서 펼쳐진다(`block:get`, 한 번에 하나, 보기 전용). 펼친 줄의 "스튜디오에서 열기"는 `window:openStudio({ blockId })`.
- **오늘 할 일** (`calendar:list`를 오늘~오늘로 조회, 줄 계산은 화면 쪽 순수 함수)
  - 오늘 칸에 보이는 일만: 오늘 마감, 오늘 시작, 오늘을 지나가는 기간. **지난 마감은 넣지 않는다.**
  - 한 블록은 한 줄. 줄 오른쪽에 마감·시작·기간을 작게 표시한다(오늘 마감이 있으면 마감, 없고 오늘 시작이면 시작, 둘 다 없으면 기간).
  - 시간은 **오늘 날짜의 시작일·마감일 시간만** 쓴다. 오늘에 시간이 여러 개면 가장 이른 것. 기간 중간 날에는 시간 없이 표시한다.
  - 순서: 시간 있는 일 시간 순 → 시간 없는 일 → 끝낸 일(줄 긋고 맨 아래). 같으면 달력 순서. 오늘 일이 없으면 "오늘은 할 일이 없어요".
  - 체크박스는 블록 단위 완료(`block:complete` / `block:reopen`). 다시 누르면 풀린다.
  - 1분마다 오늘 날짜를 확인해 바뀌면 다시 불러온다. 블록이 바뀌면 `blocks:changed`로 다시 불러온다.
- **서랍** (먹이 받기)
  - 다른 앱에서 고른 글을 서랍(또는 접힌 머리줄)에 놓으면 `method: 'drag'`. 서랍을 누른 뒤 Ctrl+V면 `method: 'paste'`. 클립보드는 붙여넣는 순간의 글만 받고, 코어는 클립보드를 직접 읽지 않는다(11장).
  - 파일·이미지 등 글이 아니면 받지 않고 "글자만 넣을 수 있어요".
  - 서랍 문구 (이벤트 → 문구는 화면 쪽 순수 함수)

    | 상태    | 언제                     | 문구                                                                                | 얼마나        |
    | ------- | ------------------------ | ----------------------------------------------------------------------------------- | ------------- |
    | 평소    | —                        | "끌어다 놓거나 눌러서 Ctrl+V"                                                       | —             |
    | 끌고 옴 | 글을 서랍 위로 끌고 있음 | 열리듯 강조, "여기에 놓아 주세요"                                                   | 놓을 때까지   |
    | 먹는 중 | 미완료 먹이 수가 1 이상  | "정리하는 중…"                                                                      | 0이 될 때까지 |
    | 끝남    | `capture:completed`      | "캘린더에 N개 넣었어요 / N개는 채워 주세요"(9.6), 블록이 없으면 "할 일이 안 보여요" | 3초           |
    | 실패    | `capture:failed`         | "못 넣었어요. 스튜디오에서 다시 시도해 주세요"(다시 시도할 수 없으면 "못 넣었어요") | 3초           |

  - "채워 주세요 N"은 늘 보이고 누르면 스튜디오를 연다. 먹이가 끝나도 스튜디오를 저절로 띄우지 않는다.
- **트레이** 메뉴: 스튜디오 열기 / 오늘 창 숨기기·보이기 / 종료. 트레이 아이콘 왼쪽 클릭은 스튜디오 열기.
- **앱은 하나만 실행한다.** 두 번째로 실행하면 새로 뜨지 않고 기존 스튜디오를 연다(트레이 아이콘이 둘 생기지 않게).
- **종료 흐름**
  - 스튜디오 X는 창 숨기기다. 앱은 트레이에 남는다. 오늘 창도 Alt+F4 등으로 닫으면 숨기기다(트레이에서 다시 보이기).
  - 처리 중인 먹이 확인은 `before-quit`에서 한다(8.2).
  - 종료가 확정되면 "종료 중" 표시를 켜서, 창 숨기기 처리가 실제 종료를 막지 않게 한다. 확인에서 취소하면 표시는 꺼진 채로 남는다.
- 앱을 켜면 오늘 창과 스튜디오를 둘 다 띄운다.
- **테스트**: 순수 계산만 한다(오늘 칸의 일 → 줄 목록, 이벤트 → 서랍 문구, 놓은 데이터에서 글 꺼내기, 저장 위치 화면 안 보정, 미완료 수 변경 알림 시점). 창·트레이는 직접 눌러 보며 확인한다.

## 10. 서버 통신 (MVP 이후)

- 코어에서만 HTTPS(REST)로 호출한다.
- 인증 토큰은 Electron `safeStorage`로 암호화 보관한다.
- API 클라이언트 모듈 하나에서 타임아웃, 재시도, 인증 헤더, 추적 ID를 처리한다.
- 요청마다 추적 ID를 붙여 서버 로그(Datadog)까지 이어서 추적한다.
- 추출 프롬프트는 서버에서 관리해 앱 업데이트 없이 개선할 수 있게 한다.

## 11. 보안·개인정보

- Electron: `contextIsolation` 켜기, `nodeIntegration` 끄기, preload로 허용 기능만 노출
- 메시지 원문 미저장 (메모리에서 추출 후 폐기)
- 창 제목 미저장 (대화방명·거래처명 노출 방지), 앱 이름만 기록
- 분석 이벤트에는 행동만 기록하고 원문·블록 내용은 절대 포함하지 않음
- 클립보드는 사용자가 붙여넣는 순간에만 읽음 (상시 감시하지 않음)
- 개발용 API 키를 넣은 빌드는 팀 내부에서만 사용, 외부 배포 금지 (키는 `.env`, Git 제외)

### 13.1 개발 순서

기반(DB·도메인)부터 쌓고 화면은 뒤에 붙인다. 깨지기 쉬운 빌드·패키징을 먼저 확인하고, 핵심 규칙은 화면 없이 테스트로 굳힌다.

| 단계                | 내용                                                                                        | 완료 기준                                                             |
| ------------------- | ------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| 0. 뼈대             | electron-vite(React + TS), ESLint·Prettier·husky, Vitest, 보안 설정                         | 개발 모드로 빈 창이 뜸                                                |
| 1. DB 기반          | better-sqlite3 + Drizzle, 스키마, 마이그레이션 생성·실행, electron-builder로 설치 파일 생성 | 설치된 앱에서도 DB 생성·마이그레이션 동작                             |
| 2. 도메인 로직      | 요소 이동·합치기·분리, 충돌 판단·자동 정리, 빈 블록 처리 (Electron 비의존)                  | Vitest 통과                                                           |
| 3. 저장소·서비스    | 소프트 딜리트 필터, 트랜잭션 + History                                                      | 서비스 테스트 통과                                                    |
| 4. IPC              | shared 타입, `IpcResult`, preload                                                           | 개발자 도구 콘솔에서 블록 생성·이동 호출                              |
| 5. 추출             | MockExtractor, 큐, Capture 상태 흐름, 시작 시 `INTERRUPTED` 처리                            | 콘솔에서 먹이 → 블록 생성 → 이벤트 수신                               |
| 6. 스튜디오 UI      | 검토함, 블록 보드, 요소 드래그, 충돌 선택, 완료·라벨·휴지통                                 | 화면에서 모든 조작 가능                                               |
| 7. 캐릭터 오버레이  | 투명·항상 위 창, 드래그 드롭·붙여넣기, 트레이, 캐릭터 반응                                  | 다른 앱에서 먹이 → 스튜디오에 블록 표시                               |
| 8. 캘린더           | 목업 캘린더 화면 (7.5 표시 규칙)                                                            | 날짜별 표시                                                           |
| 9. 캘린더 중심 흐름 | 블록 분류(7.6), 요소 직접 추가(7.7), 탭 없는 한 화면(캘린더 + 채워 주세요 목록), 알림 쌓기  | 할 일·날짜가 있으면 손대지 않아도 캘린더에, 빠진 블록만 목록에서 채움 |
| 10. 오늘 창         | 캐릭터 → 오늘 창(오늘 할 일, 투명도, 접기, 서랍 먹이 주기), 완료 체크박스                   | 오늘 할 일이 떠 있고, 체크로 끝내고 서랍으로 먹이를 줌                |
| 11. 실제 추출       | DirectLlmExtractor (개발용 API 키)                                                          | 실제 메시지로 추출                                                    |
| 12. 마무리          | Playwright E2E, 배포 빌드 정리                                                              | 영상 촬영 가능                                                        |

- 9단계는 8단계까지 만든 뒤 "검토함이 사람에게 일을 너무 시킨다(캘린더에 직접 적는 것보다 빨라야 쓸 이유가 있다)"는 판단으로 끼워 넣었다. 원래 9·10단계는 10·11단계로 밀었다.
- 10단계는 "캐릭터는 평소 떠 있어도 쓸모가 없다. 오늘 할 일이 떠 있어야 켜 둘 이유가 생긴다"는 판단으로 끼워 넣었다. 실제 추출과 마무리는 11·12단계로 밀었다.
